# Agent Basic Concepts (Easy-to-Understand Edition)

## 1. What is an AI Agent?

**An AI Agent is a "digital employee that can figure out how to complete tasks on its own when given a goal."**

### Ordinary LLM vs AI Agent

Many people think LLM and AI Agent are the same thing, but they actually have significant differences.
- LLM: It answers whatever you ask, it can only talk but cannot act
- Agent: Just tell it the final goal, and it can autonomously plan and execute

---

## 2. What is a ReAct Agent?

ReAct Agent is the most commonly used "thinking approach" for AI Agents, teaching AI to **"think while acting."**

### Origin of the ReAct Name

**ReAct = Reasoning + Acting**

### The Core of ReAct Agent: TAO Loop

The workflow of a ReAct Agent can be memorized with three letters: **TAO Loop**

```
┌─────────────────────────────────────────┐
│                                         │
│   T = Thought (Thinking)                │
│   The agent's "inner monologue", AI first thinks clearly
│   "What should I do now? Why should I do this?"
│                                         │
│              ↓                          │
│                                         │
│   A = Action (Acting)                   │
│   Based on the thinking result, call appropriate tools to execute
│                                         │
│              ↓                          │
│                                         │
│   O = Observation                       │
│   See what results the tool returned, what new information was obtained
│                                         │
│              ↓                          │
│        Loop continues...                │
└─────────────────────────────────────────┘
```

Simply put, it's a **"thinking + tool calling"** loop until the task is completed.

**Tool is a very important concept!**

LLM itself can only generate text and cannot perform actual operations. Tools enable agents to:
- Query databases
- Call APIs
- Execute calculations

### Tools Field Explanation

From the above request content, we can see that the `tools` field defines a list of tools. Each tool contains:

| Field | Description |
|-------|-------------|
| `name` | Tool name |
| `description` | Tool description, tells the LLM what this tool is for |
| `input_schema` | JSON Schema definition of input parameters |

The example defines three tools:
1. **getCurrentTime**: Get the current time
2. **lark cli agent**: Feishu office assistant
3. **load_skill_through_path**: Load skills

## 4. Memory

Since large models have a **stateless design**, simply put, LLM can only generate output based on the input you send to it, and cannot remember the content of your previous conversations.

### The Role of Memory

Memory is used to store conversation history.

Take `io.agentscope.core.memory.InMemoryMemory` in AgentScope as an example:

```java
private final List<Msg> messages = new CopyOnWriteArrayList<>();
```

AgentScope uses a `List` to store conversation history, each conversation history is a `Msg` object, corresponding to `messages` in the captured content.

---

## 5. Session

### The Role of Session

Session is used to manage multiple independent conversation sessions.

Take `io.agentscope.core.session.InMemorySession` as an example:

```java
private final Map<String, SessionData> sessions = new ConcurrentHashMap<>();
```

Memory data is ultimately stored in `SessionData`, and different sessions are distinguished by `session_id`.

## 6. Skill

### The Essence of Skill

Skill became very popular at the end of 2025. Many people think Skill can do anything, and they write a Skill for everything.

**So what is the essence of Skill?**

Simply put: **Skill = Prompts + Scripts**.

### Progressive Loading of Skills

Skills are not all loaded to the large model at once, but **loaded on demand**—first tell the large model "what skills you have available", and then load the detailed content when the large model determines it needs them.

The benefits of this approach:
- **Save Tokens**: Don't need to stuff all the complete content of all skills into the context
- **On-demand Activation**: The large model autonomously determines which skill is needed based on the task

Let's look at how skills are progressively loaded from the most intuitive packet capture. In the **"Example of Content Sent by Agent to LLM"** section, there is a complete captured request, where the `system` field translated to English is roughly:

```markdown
You are an assistant

## Available Skills

<usage>
Skills provide specialized capabilities and domain knowledge. Use them when they match your current task.

How to use skills:
- Load skill: load_skill_through_path(skillId="<skill-id>", path="SKILL.md")
- The skill will be activated and its documentation loaded with detailed instructions
- Additional resources (scripts, assets, references) can be loaded using the same tool with different paths

Path Information:
When you load a skill, the response will include:
- Exact paths to all skill resources
- Code examples for accessing skill files
- Usage instructions specific to that skill

Template fields explanation:
- <name>: The skill's display name
- <description>: When and how to use this skill
- <skill-id>: Unique identifier for load_skill_through_path tool
</usage>

<available_skills>

<skill>
<name>mysql-table-design</name>
<description>MySQL table design specifications. Use this skill when designing database table structures, including: creating new tables, reviewing table designs, checking if existing tables conform to specifications. Trigger scenarios: requesting table design, table creation, reviewing table structure, checking table naming or field definitions, etc.</description>
<skill-id>mysql-table-design_filesystem-workspace-5_skills</skill-id>
</skill>

</available_skills>
```

### What Does This Content Do?

Breaking it down, it does three things:

| Function | Description |
|----------|-------------|
| Tells the large model "you have a toolbox" | Lists all available skill names and brief introductions through `<available_skills>` |
| Teaches the large model "how to open the toolbox" step by step | Gives precise tool calling format: `load_skill_through_path(skillId="xxx", path="SKILL.md")` |
| Clearly tells the large model "when to use which tool" | Each skill has a `<description>` describing trigger scenarios, establishing an extensible skill system |

Meanwhile, the `tools` field defines the `load_skill_through_path` tool for actually loading skill content.

### Skill Loading Process Summary

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   1. Agent lists summary information of available skills in system
│      (skill name + short description)                 │
│                                                      │
│                      ↓                               │
│                                                      │
│   2. LLM determines current task needs a certain skill
│      (Thought: "This task requires designing a MySQL table...") │
│                                                      │
│                      ↓                               │
│                                                      │
│   3. LLM calls load_skill_through_path tool           │
│      (Action: load mysql-table-design skill)          │
│                                                      │
│                      ↓                               │
│                                                      │
│   4. Agent returns the complete content of the skill (prompts + scripts)
│      (Observation: get detailed MySQL table design specifications) │
│                                                      │
│                      ↓                               │
│                                                      │
│   5. LLM continues executing task based on skill content
│      TAO loop continues...                           │
│                                                      │
└──────────────────────────────────────────────────────┘
```

## 7. SubAgent

### When Do You Need a SubAgent?

When the functionality far exceeds what a single Agent's context window can handle, multiple Agents need to work together through division of labor.

### The Form of SubAgent

In the captured request, **SubAgent and ordinary Tool look exactly the same**—they are both defined in the `tools` field, and the LLM doesn't know it's calling an independent Agent.

Take `lark cli agent` as an example:

```json
{
  "input_schema": {
    "type": "object",
    "properties": {
      "session_id": {
        "description": "Session ID for multi-turn dialogue. Omit to start a NEW session. To CONTINUE an existing session and retain memory, you MUST extract the session_id from the previous response and pass it here.",
        "type": "string"
      },
      "message": {
        "description": "Message to send to the agent",
        "type": "string"
      }
    },
    "required": ["message"]
  },
  "name": "lark cli agent",
  "description": "You are a professional Feishu (Lark) office assistant with the ability to directly operate the Feishu platform through the official lark-cli tool. You can understand users' natural language instructions, automatically call appropriate Feishu CLI commands to complete tasks, and return results in a clear and understandable way."
}
```

### SubAgent vs Ordinary Tool

| Comparison Dimension | Ordinary Tool | SubAgent |
|---------------------|---------------|----------|
| Essence | A specific function/interface | An independent agent |
| Processing Logic | Fixed logic, input→output | Has its own LLM calls, can autonomously think and act |
| Session Management | Stateless | Usually has `session_id`, supports multi-turn dialogue |
| Context | Shares main Agent's context | Has independent context window |
| Suitable Scenarios | Simple clear operations (write files, check time) | Complex multi-step tasks (Feishu office assistant) |

**Core Difference**: SubAgent has its own TAO loop internally, it can autonomously plan and execute subtasks, while ordinary Tool just executes a fixed operation.
